# FUCK AI

作者为 Skai Uijing。AI 是协作者，不得擅自接管作者的实现、研究或表达。以用户当前明确指令为准，不得把过去对某次任务的授权扩展为对整个项目的授权。

## 1. 保护作者的工作

- `scp.c`、`scp.h` 和 `lib/` 属于核心代码，默认禁止修改。
- 作者手写、没有 AI 参与的其他代码，同样必须经过作者明确同意才能修改。
- 作者原有 README、论文、研究笔记等文档默认禁止修改；只有作者明确指定的部分可以改动。
- 修改包括删除、移动、重命名、格式化、替换、自动生成覆盖以及 Git 回退。声称“修复 bug”或“删除历史包袱”不构成授权。
- 来源不清楚时，先查 Git 和历史记录；仍不能确定，就按作者内容保护，不能自行认定为 AI 生成。
- 发现问题可以检查、指出并提出具体修改方案，不能先改再通知。

## 2. 核心代码的审核边界

- 必须由作者亲自编写修改，或由作者给出至少伪代码级的具体步骤并明确授权 AI 实现。只有“检查”“测试”“有问题吗”等要求不允许修改核心代码。
- 严格按作者给出的算法步骤、位置和字段执行；不得擅自换成另一种实现或顺带重构。
- 每次交给作者审核的核心增量默认不超过 20 行，以最近一次作者已审核状态为比较基准，按对应 diff 的新增行数加删除行数计算；跨文件合计，不按净增行数计算。作者明确要求一次性给出完整实现时，按该要求执行。
- 超过审核上限的任务应真实分段实现、逐次展示 diff 并等待审核，不得先全部写完再假装分批。审核分段不等于 Git 提交分段，不为保存审核中的中间状态创建 commit。
- 提交以完整的逻辑变更为单位。同一件事的实现、配套测试和必要文档，应在全部审核和必要检查通过后放入同一次 commit；不要提交一半实现，再用后续 commit 反复补齐或修改同一半实现。不要把 Git 提交历史当草稿纸。
- 展示具体 diff 和修改理由后交给作者审核。未经本次明确授权，不提交、不 push；作者要求回退时只撤销 AI 对应修改，保留作者的改动。
- 用户说“提交”时，默认包含 git commit 和 push 到对应 GitHub 分支。完整逻辑变更形成最终 commit 后再 push，让 GitHub 对完整状态运行一轮 CI；不要为每个审核片段或小修订分别提交、push，也不要重复启动已由 push 触发的同批工作流。
- 遵循现有代码风格：优先现成的链表操作和 BSD 序号比较宏，避免不必要的 uint64、魔数、注释、辅助函数及抽象。不得重新引入作者已经明确排除的精度或极端算术讨论。

## 3. AI 生成内容的修改权限

- 已明确为 AI 生成的测试代码和文档，可以在作者当前任务范围内修改、合并或删除，不必逐项重复请求许可。
- 这不允许修改它们调用的核心代码，也不允许删除作者原有脚本或文档。
- `test/analyze_scp.py` 和 `test/fig.py` 是作者指定保留使用的原绘图脚本；不得擅自替换、删除或改变图形风格。修改它们需获得明确授权。
- 虚拟网络与真实 UDP 测试共用传输逻辑。曲线读取协议栈自己的日志，调用原绘图脚本；批量扫参数为每种条件、每个连接保留独立图片和日志，不能只画总览。

## 4. 不制造垃圾

- 开始测试、实验或重跑前，先复述从最初问题到最终目标的完整计划、已完成与未完成事项、本轮所处阶段；不能只说明当前局部操作。
- 先完善并验证基线的协议栈、虚拟网络与公共测试能力，再同步到现有研究分支。研究分支复用同一套核心、网络、时间推进及公共传输代码，只增加明确的实验配置、入口和只读观测；共同能力不得在研究分支另写一份。
- 编写或修改测试前，先说明测试方案：测试什么、环境和输入是什么、如何判断通过、输出哪些日志和图片。区分虚拟网络仿真与真实 Linux UDP 测试，不把仿真称为真实测量。
- 优先复用已有实现，删除确实无用的 AI 代码；不要增加重复采样、重复绘图、重复报告、无效选项、备用实现或无用途文件。
- 删除前核对调用、构建、CI 和文档引用，不能仅凭名字或文件年龄判断“多余”。
- 完整性、单元和功能测试可以简洁输出 PASS/FAIL；大数据传输和网络参数测试保留运行曲线、配置、日志和结果，失败与超时也尽量保留诊断日志。
- 不为测试通过而改核心逻辑、隐藏失败或删除有效测试。报告实际执行结果；未执行的 Linux、GitHub 或长时间测试必须明确说明。

## 5. 研究和沟通

- 保留作者提出的问题、三明治结构和研究思路；不得把 AI 的整理、翻译或推导辅助写成 AI 原创，也不得夸大社区认可。
- 明确区分已证明结论、特定调度器结果、仿真数据和未证明猜想。不能为了简短把直觉改写为已完成的证明。
- 只完成当前授权任务，说明具体修改、验证结果和尚未验证部分。不要擅自提交、push，或改写、合并已经发布的提交历史。

## 6. 先说明意图，再介绍内容

- AI 生成或修改文档、设计方案及其交付入口时，必须先说明它要解决什么问题、为什么这样设计、适用范围，以及读者能用它完成什么；不能只罗列文件、功能、公式或运行命令。
- 说明必须写进读者实际会看到的入口，不能只留在聊天记录或深层目录。研究分支的根 README 应首先说明研究什么、与基线的关系，并链接论文、实验和复现指南；复现指南应先说明复现哪项研究、哪批结果，执行什么对象，以及如何判断复现成功。
- 按首次接触项目的读者组织内容：先交代目的与背景，再给使用步骤和技术细节。更新成果时同步检查入口说明，修正过时或相互矛盾的描述；已有相关文档优先补充，不另造重复文档。
