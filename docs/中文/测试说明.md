# SCP 测试与复现

[English test guide](../../test/README.md) · [项目概览](README中文.md) · [API 手册](使用手册.md)

本指南说明如何验证传输完整性、观察不同网络环境下的行为，以及复现 pacing 研究。
main 负责功能、鲁棒性、收敛与吞吐质量；SS/CA 研究分支负责固定反馈条件下的机制研究。
先选对执行对象和环境，再看图与指标。所有命令从仓库根目录运行；数据量使用二进制单位。

## 构建与快速验证

需要 C 编译器、CMake、Python 3；绘图另需 matplotlib、numpy、pandas。
Windows 的可执行文件带 `.exe`，Linux netem 命令只适用于 Linux。

```sh
cmake -S test -B test/build -DCMAKE_BUILD_TYPE=Release
cmake --build test/build -j
ctest --test-dir test/build --output-on-failure
python3 -m pip install matplotlib numpy pandas
python3 test/virtual/sweep.py test/build/scp_virtual --profile quick --out test/results/quick
```

当前 CTest 共 17 项：11 项虚拟测试和 6 项真实 UDP 测试。CTest 使用 `--no-plot`，不依赖绘图库。
可通过 `-L virtual` 或 `-L real` 分开执行。CI 另以 AddressSanitizer 和泄漏检测运行虚拟测试。
`quick` 是 21 次 1 MiB、三 Seed 的轻量场景检查，不等于大规模吞吐基准。

## 架构与完整性

```text
CTest / run.py / virtual/sweep.py
              ↓
common/transfer.c：数据生成、逐字节验证、校验和交换、关闭
              ↓
实际 scp.c：发送队列、pacing、ACK、重传、窗口更新
              ↓
virtual/vnet.c：配置网络＋虚拟时钟
或 common/udp_runner.c：实际 socket＋真实时钟
```

两个后端共用传输逻辑。A 生成数据，B 对生成数据逐字节核对，双方计算有序流 FNV-1a-64；
B 通过 SCP 返回长度和校验和，A 验证后关闭，两端必须完成关闭。生成模式不写载荷文件。
真实文件测试另核对文件长度和 SHA-256。应用发送积压约为 1 MiB，不等于 cwnd。

虚拟传输测试沿用生命周期测试的方式包含未改写的 `scp.c`，只观测核心分配和定时器树。
逐 tick 检查发送序号顺序，正确计入 FIN 占用的序号；实际 transport 回调检查首次 DATA 的连续性，
重复序号计入重传。关闭后检查核心分配、流与定时器是否清空。RTO 观测回调累加次数后仍调用原控制器回调。
核心 `timeout_count` 是连续计数，不能拿结束时的值当全程累计次数。

## 虚拟网络与时钟

默认 1 tick = 1 μs，`vnet_step()` 每次只递增一个 tick，依次处理正向到达、反向到达和核心定时器；
调用方随后推进应用。它不跳时间，也不生成虚假的 ACK 或代算 cwnd。ACK 必须由对端核心处理 DATA 后产生。

`--mbps` 设置每方向速率，序列化之后再传播；`--delay-ms` 是单向传播延迟。
完整反馈 RTT 还可能包含序列化、排队和 tick 量化，不能直接把 `2 * delay_ms` 当作实际反馈时间。
`--loss-ppm` 是双向独立随机丢包，包含 DATA、ACK 和控制包，种子可复现。

`--queue-packets N` 限制每方向序列化区的包数，包括正在发送的包，不包括已进入传播阶段的包。
队满时丢弃新到包，不占用额外链路服务时间；默认 0 为无上限。`--mbps 0` 禁用序列化。
当前不模拟 Wi-Fi 竞争、链路层重试、主动复制或主动乱序。

```sh
cmake -S test -B test/build-ms -DSCP_TEST_TICK_SCALE=1
cmake -S test -B test/build-us -DSCP_TEST_TICK_SCALE=1000
```

两种配置都逐 tick 推进。真实 UDP 始终使用默认 1 ms 刻度。初始 RTO 是 1000 ms；
获得 RTT 后按现有估计器更新，边界为 200–2000 ms。无 SRTT 时 pacing 使用的仍是物理 1 ms 回退。

独立运行并保存完整核心日志和原分析器曲线：

```sh
python3 test/run.py test/build/scp_virtual --backend virtual --bytes 1073741824 --out test/results/virtual-1g
```

直接运行二进制可使用全部网络参数，结果 `summary.json` 写入当前目录：

```sh
./test/build/scp_virtual --bytes 8388608 --mbps 100 --delay-ms 25 --loss-ppm 0 --queue-packets 20 --seed 7
```

二进制还支持 `--timeout-ms`、`--cc`（AIMD=1、PROB=0）和 `--send-backlog-bytes`。
`run.py` 没有透传 `--queue-packets`，有限队列使用二进制或 sweep 配置。

## 扫参与质量指标

唯一矩阵配置是 [network_sweep.json](../../test/virtual/network_sweep.json)。

|---|---:|---|
| quick | 21 | 1 MiB，三 Seed，开发时检查 |
| broad | 300 | 8 MiB，广泛速率、RTT、丢包组合 |
| large | 152 | 144 次 1 GiB、8 次 10 GiB |
| stress | 8 | 100 GiB，仅显式选择 |
| scenarios | 200 | 64 MiB、五 Seed、0%–5% 丢包，默认 CI |
| scenarios-1g | 48 | 1 GiB、三 Seed、四档丢包 |
| shallow-stress | 3 | 8 MiB、20 包队列、零随机丢包 |

| 场景 | 基础 RTT | Mbps | 队列 | 重点 |
|---|---:|---:|---:|---|
| wifi-simplified | 10 ms | 100 | 无上限 | 抗损保持率、Seed 离散度和恢复曲线 |
| wan | 50 ms | 100 | 100 包 | 缓冲膨胀、重传与丢包比 |
| intercontinental | 200 ms | 100/1000 | 无上限 | 无损配置零 RTO、启动速度；有损配置恢复能力 |
| shallow-stress | 50 ms | 100 | 20 包 | pacing 削峰、尾丢弃恢复、无死锁完成 |

```sh
python3 test/virtual/sweep.py test/build/scp_virtual --profile scenarios --jobs 2 --out test/results/scenarios
python3 test/virtual/sweep.py test/build/scp_virtual --profile shallow-stress --out test/results/shallow
```

可用 `--config`、`--shard-index`、`--shard-count` 指定配置与分片。
合并时输入目录包含 `shard-*`：

```sh
python3 test/virtual/sweep.py --merge test/results
python3 test/plot.py test/results
```

| 字段 | 解释 |
|---|---|
| checksum_ok | 字节数、逐字节验证及双端 FNV-1a/返回校验和 |
| sequence_ok / cleanup_ok | 序号守恒／核心资源清理 |
| timeouts | 全程两端 DATA RTO 累计；`timeouts_a/b` 分开记录 |
| retrans_packets | 双向重复 DATA 发送数 |
| spurious_rexmit_ratio | 重传数 / max(1, 全部网络丢包)，不是伪重传识别器 |
| srtt_avg_ms / srtt_max_ms | 发送方处理 ACK 后的 SRTT 均值／最大值；排除未初始化零值，按 ACK 加权 |
| bufferbloat_ratio | 平均 SRTT / 双向传播 RTT；零延迟时为 -1 |
| startup_rtts_to_80pct | 从首次 DATA 到首次达到观测峰值 cwnd 的 80%，以基础 RTT 计；不是 80% BDP，无法计算为 -1 |
| goodput_mbps | 包含启动、确认排空与关闭时间的有效吞吐 |

完整性、序号和清理是所有场景的硬门禁。`transfer_success` 表示原生传输完成；
`sweep.csv` 的 `success` 还包含场景门禁。只有无损跨洲配置启用 `require_zero_rto`。
随机丢包导致的必要 RTO 必须记录，但不一律判失败。未完成、校验失败、死锁超时不能隐藏。

## 图表、产物与失败复现

扫参流式读取核心 stdout，每连接最多保留 256 个状态点，保存 `curve.csv`、`curve.png`、
`config.json` 和 `summary.json`。精简只影响图表，不减少全程完整性检查和逐 ACK 指标。
成功扫参不写原始文本日志；失败保留最多 32 行诊断和精确的单行 `Repro:` 命令。
`plan.json` 记录源码提交、工作区状态、二进制 SHA-256 和完整参数。

`report.md`、`sweep.csv`、`sweep.png`、`bufferbloat.png` 是聚合入口。
图中种子点、中位线与 min/max 包络按场景、带宽、延迟、队列和载荷分别分组；失败门禁显示红叉。
缺少分片或存在失败时，合并返回非零。复现失败应保留原源码、构建刻度和配置，在单独目录执行报告命令；
`Repro:` 是标签，实际执行它后面的命令。质量门禁失败可能仍得到完整传输，须检查对应指标。

GitHub Actions 使用八个分片，独立执行 CTest、ASan、虚拟 1 GiB 与 Linux localhost UDP 文件 1 GiB：

- `network-report`：聚合表与 PNG；Summary 提供下载入口，下载后的 Markdown 可显示同目录图片。
- `network-shard-*`：精简单例结果，不包含大规模原始逐包日志。
- `transfer-1g-curves`：独立传输图表；`transfer-1g-logs` 仅失败时上传。

附件保留 14 天，不把大结果重复放进 Git 或 Release。附件过期后按配置重跑。

## 真实 UDP、文件与 Linux netem

```sh
python3 test/run.py test/build/scp_udp --out test/results/udp-1g
python3 test/run.py test/build/scp_udp --bytes 8388625 --mode prob --out test/results/prob
python3 test/run.py test/build/scp_udp --file-test --bytes 1073741824 --out test/results/file-1g
```

`--file path` 使用已有非空文件，其大小决定传输量；B 写入结果目录中的 `received.bin`，
两端长度、SHA-256 和 SCP 校验和均需匹配。原始载荷文件不上传 CI。
手动双端顺序为先 B 后 A，参数格式 `A|B [peer-ip] [bytes] [aimd|prob|pacing]`；双方载荷和模式应一致。
`pacing` 使用 AIMD，观测的是 transport 回调，不是网卡实际出线时间。

```sh
test/build/scp_udp B
test/build/scp_udp A 127.0.0.1
```

Linux namespaces 和 netem 另建受控路径；运行器不会自动创建拓扑：

```sh
sudo bash setup_scp_netns.sh setup 100mbit 10ms 0% 1000
sudo bash setup_scp_netns.sh show
sudo python3 test/run.py test/build/scp_udp --netns --file testA.bin --timeout 3600 --out test/results/linux-file
```

先准备 `testA.bin`。拓扑为 `scp-c ↔ scp-r ↔ scp-s`，路由器两个出口分别施加带宽、延迟、丢包和队列。
`--netns` 默认对端为 `10.0.2.1`，可用 `--peer` 覆盖。历史实验的 5 Mbps、单向 50 ms、1000 包队列，
与当前 CI localhost UDP、虚拟场景都不同，不能混写成同一组实测。

双流公平性模式为 `prob-prob`、`prob-aimd`，数量参数变为秒：

```sh
python3 test/run.py test/build/scp_udp --mode prob-aimd --seconds 10 --out test/results/fairness
```

接收方从首次载荷起使用共同测量区间，报告实际接收 goodput 和 Jain 指数；发送方指标仅描述入队。
停止测量后仍会排空和关闭，关闭流量不计入测量。localhost 的短测试只检查存活性，公平性结论需要共同受限链路。

## 模型与实际执行

研究流程为 idea → 数学算法模型 → 可审核 Python → 实际 SCP。Python 模型不是协议栈执行的替代。
两层都使用保留 next-slot 的调度：每批 `max(next_slot, now)`，先赋时刻，再加该包 gap，空队列保留尾槽。
Python 默认实数窗口；SCP 使用整数字节与 CA 余数。SCP 为 Q16 gain、Q32.32 tick 预约。
数学公式、模型观察、真实核心观察分别标记，比较同 ACK 序号与同时间也要分开。

```sh
python3 test/models/pacing.py --mode ca --gain 1.647918701171875 --bytes 100100 --repeats 3 --trace --out test/results/model-small
python3 test/models/check.py --runs test/results/model-small --out test/results/model-check
python3 test/models/pacing.py --mode ss --out test/results/python-ss
python3 test/models/pacing.py --mode ca --gain-grid ca-critical --out test/results/python-ca
```

`--ca-update real|byte-floor|byte-remainder` 分别隔离实数窗口、历史字节截断和当前余数机制；
`--ack-windows` 保存逐 ACK 窗口。原生 gain 对照使用 `107998/65536` 的实际值。
Python 全 MSS 会把 1 GiB 向上补足 846 字节；原生 SCP 精确传输 1 GiB，最后一包 584 字节。
因此同 ACK 比较应排除原生短尾包，组跨度应排除末端不完整组。

完整包组的 `L` 是实际首尾跨度，occupied span 另含尾间隔，`D` 是累计组首漂移。
固定 RTT 分箱、完整包组和内部包密度不可混用。确定性无损三次重复用于核对一致性，不产生随机置信区间。

真实核心复现分别使用 [SS 分支](https://github.com/skaiui2/SCP/tree/research/slowstart-nextslot-q16-20261022/reproduction)
和 [CA 分支](https://github.com/skaiui2/SCP/tree/research/ca-nextslot-q16-20261022/reproduction)。
已核验完整运行：[SS 40340718507](https://github.com/skaiui2/SCP/actions/runs/40340718507)、
[CA 40340725047](https://github.com/skaiui2/SCP/actions/runs/40340725047)。各含 22 gain × 3 和三次原生策略对照。
研究网络使用每方向 50 ms、无丢包、无序列化，实际反馈 100 ms；不能用 main 的串行链路矩阵代替。
研究分支记录自己的冻结基线，不因 main 更新就把旧数据改标签。

需要重新分析已有成功分片时，使用 Actions 的 `Reanalyze completed SCP pacing transfers`，
选择研究分支和来源 run ID。它核对 22 个 gain 作业后下载并重算，不重新执行原生传输；
产物分别记录原生来源、分析版本和工作流版本。附件过期则需要重新运行。

```sh
python3 test/plot.py A.log --stream-fd 1 --out test/results/state-plots
```
